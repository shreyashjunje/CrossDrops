# Code review, 2026-11-03

Review of `main` at `de85956` (Phase 7). Static review only: the code was read, not run. No phones and no Flutter SDK were used; CI (analyze and unit tests) is green on this commit. Line numbers refer to that commit.

Severity: **High** (security or data loss), **Medium** (wrong behavior users will hit), **Low** (edge cases). **Confirmed** means the path was traced end to end in the code; **Plausible** means one step depends on timing or OS behavior and still needs a device check.

## Verdict

- The design is sound and well documented: receiver-as-server, streamed PUT with resume, SHA-256 verify, pinned TLS 1.3, signed sender challenge, rate limits, no-copy saving on Android. The decision log is unusually good.
- Nothing is proven on devices yet. The README says Phases 1 to 6 are "built and tested on devices", but every Results table in [DEVICE_TESTS.md](DEVICE_TESTS.md) is empty and [BENCHMARKS.md](BENCHMARKS.md) has no numbers. The only recorded device run is a 1.2 MB video from a Samsung to a PC ([TODAY-2026-11-02.md](TODAY-2026-11-02.md)). Fill in the tables, or change the README wording to match.
- Release blockers: the app id is still `com.example.crossdrop` (Android and iOS), Android release builds are signed with the debug key ([build.gradle.kts](../android/app/build.gradle.kts)), there is no LICENSE file, and the `pubspec.yaml` description is "A new Flutter project."
- Positioning: the closest product is LocalSend (open source, also on desktop). Being iPhone and Android only needs a clear reason to pick CrossDrop; speed numbers from the Phase 7 comparison would be that reason.

## Bugs

### High

**H1. A man in the middle can make the pairing codes match (Confirmed).**
- [peer_auth.dart:44](../lib/core/security/peer_auth.dart#L44) commits only to the sender nonce, not to the sender's certificate or fingerprint.
- [sender_auth.dart:76-106](../lib/core/server/sender_auth.dart#L76-L106) accepts any certificate at `/v1/auth`, after the receiver nonce is known, and derives the code from that fingerprint.
- The fingerprint is SHA-256 of the whole DER ([fingerprint.dart:10](../lib/core/security/fingerprint.dart#L10)) and the certificate's self-signature is not checked ([device_credentials.dart:134-158](../lib/core/security/device_credentials.dart#L134-L158)), so changing an ignored byte gives a new fingerprint for the same key.
- Attack: the attacker poses as the receiver to the sender (spoofed mDNS or a typed address) and as a sender to the real receiver. Once the sender reveals its nonce, the attacker knows the sender's code and grinds about 10^6 certificate variants until the receiver's code matches. That takes under a second, well inside the 60 s challenge lifetime. Both phones show the same code, the user taps Accept, and the attacker can relay or replace files and become trusted.
- Fix: commit to the sender fingerprint together with the nonce, for example `SHA-256("crossdrop-commit-v2\n" + senderFp + "\n" + senderNonce)`, and check it at `/v1/auth`. Bump the protocol version.

**H2. Integer overflow bypasses the free-space check (Confirmed).**
- [models.dart:102](../lib/core/protocol/models.dart#L102) only rejects `size < 0`; there is no upper bound.
- `totalBytes` ([models.dart:219](../lib/core/protocol/models.dart#L219)), the session total ([receive_server.dart:120](../lib/core/server/receive_server.dart#L120)) and `offered + committed + reserve` ([receive_server.dart:840](../lib/core/server/receive_server.dart#L840)) wrap in 64-bit ints.
- Example: four files of 2^62 bytes plus one of 1 KB sum to 1 KB. The checks at :850 and :884 pass and the Accept screen ([incoming_request_screen.dart:224](../lib/features/receive/incoming_request_screen.dart#L224)) shows "1 KB". After Accept (or auto-accept), the sender can write until the disk is full.
- Fix: cap each file (for example 1 TB) and the offer total, and sum with an overflow check.

**H3. Leaving the hotspot screen while it starts leaves the hotspot running (Confirmed).**
- [hotspot_controller.dart:94-121](../lib/features/hotspot/hotspot_controller.dart#L94-L121): `onDispose` calls `_service.stop()` while `start()` is in flight. Kotlin `stop()` ([HotspotChannel.kt:156-159](../android/app/src/main/kotlin/com/example/crossdrop/HotspotChannel.kt#L156-L159)) closes a reservation that is still null and leaves `pendingStart` set; `onStarted` ([HotspotChannel.kt:107-120](../android/app/src/main/kotlin/com/example/crossdrop/HotspotChannel.kt#L107-L120)) then stores it, and Dart returns at `if (!ref.mounted) return;` without stopping it.
- A second window: disposing during `await list()` (line 109) means `start()` runs after dispose.
- Result: the LocalOnlyHotspot stays up with no UI until the activity is destroyed.
- Fix: in Kotlin, have `stop()` cancel a pending start (close the reservation in `onStarted` if a stop came first); in Dart, call `_service.stop()` instead of returning when not mounted.

**H4. iOS cold start can delete files that were just shared in (Plausible).**
- [share_listener.dart:49](../lib/features/send/share_listener.dart#L49) takes the share inbox after the first frame and [share_inbox.dart:272-275](../lib/platform/share_inbox.dart#L272-L275) moves it to `outgoingStaging/share-<id>`.
- At the same time `unfinishedTransfersProvider` ([unfinished_transfers.dart:47](../lib/features/transfer/unfinished_transfers.dart#L47)) runs `cleanStaging`, which deletes every batch no unfinished send uses, including the new `share-*` folder.
- Seen as: "N files ready", then Send fails with "Nothing could be prepared". Needs a device check of the ordering.
- Fix: skip `share-*` folders younger than a few minutes in `cleanStaging`, or run the cleanup before taking the inbox.

### Medium

**M1. Receive sessions are never freed (Confirmed).** `_sessions` is added to at [receive_server.dart:819](../lib/core/server/receive_server.dart#L819) and never removed from. Any key pair can offer 10,000 files (4 MB body) and cancel at once, which frees the per-sender and open-session slots but keeps the session, its file map and up to 10,000 DB rows. At the rate limit that is about 180 offers per hour per IP; the receiver runs out of memory, and every offer also shows an Accept prompt. Fix: drop terminal sessions from memory after a short grace period.

**M2. One hash isolate per file, never stopped (Confirmed).** Each PUT at `offset=0` spawns a `Sha256Isolate` ([receive_server.dart:1108](../lib/core/server/receive_server.dart#L1108)). A PUT that ends short of the size keeps it alive (:1205, :1218). An accepted sender can PUT 1 byte to each of 10,000 files and leave 10,000 isolates running; paused sessions never expire. Fix: one hasher per session (or a small pool), and stop it when the PUT ends short.

**M3. A paused receive keeps the wakelock and foreground service forever (Confirmed).** `_trackKeepAlive` ([receive_controller.dart:532-547](../lib/features/receive/receive_controller.dart#L532-L547)) only ends keep-alive on terminal states; `paused` is not terminal. After an iPhone sender goes to the background or gives up on the network, the receiver's screen stays on and "Receiving from X" stays up. The wakelock also keeps the app visible, so the hide-and-suspend path never runs. Fix: end keep-alive on `paused` and begin it again on `transferring`.

**M4. Pause is lost between uploads (Confirmed).** `requestPause()` ([upload_client.dart:506-508](../lib/core/client/upload_client.dart#L506-L508)) only sets the flag when `_active != null`, which is set after `_ensureToken` and `openUrl` in `put`. A pause during `fileStatus`, `_confirm`, auth or connect ([send_session.dart:640-656](../lib/core/engine/send_session.dart#L640-L656)) is dropped and the whole file uploads. On iOS, `onBackground` ([send_controller.dart:447-451](../lib/features/send/send_controller.dart#L447-L451)) subscribes after `pause()` already emitted `paused`, waits the full 10 s, and the app is suspended mid-PUT. Fix: keep the pause request on the client regardless of `_active` and check it right after the PUT opens.

**M5. Cancel while connecting or offering shows a network failure (Confirmed).** With `_sessionId` still null, `cancel()` ([send_session.dart:394-415](../lib/core/engine/send_session.dart#L394-L415)) only force-closes the HttpClient, so the in-flight `info()` or `offer()` fails as `network` and `_offer` reports `failed: network`. If the offer already reached the receiver, no `cancelSession` is sent; if the receiver accepts, the session sits in `accepted` with no uploads and holds keep-alive (see M3). Fix: check `_localCancel` in `_offer` and map to `cancelled`; after the offer returns, send `DELETE` if a cancel came in.

**M6. iOS receive server may not come back after suspension (Plausible).** [receive_controller.dart:352-358](../lib/features/receive/receive_controller.dart#L352-L358) restarts the server only when `_suspended` is true, which needs the 30 s idle timer; iOS suspends an idle app about 5 s after it is hidden. If iOS reclaims the listening socket (TN2277), the phone advertises a dead port after unlock. Needs a device check: lock an idle iPhone for a minute, unlock, and send to it.

### Low

- **L1. Two saves can overwrite each other (Confirmed).** [file_name_sanitizer.dart:70-85](../lib/core/storage/file_name_sanitizer.dart#L70-L85) picks a free name with `existsSync`, and the `rename` in [file_store.dart:207-209](../lib/core/server/file_store.dart#L207-L209) runs later and silently replaces an existing file on POSIX. Two concurrent `/complete` calls with the same name both report "saved" at one path. Fix: create the destination exclusively (`File.create(exclusive: true)`) before moving.
- **L2. `/complete` does not re-check state after reading its body (Confirmed).** [receive_server.dart:1261-1279](../lib/core/server/receive_server.dart#L1261-L1279) checks the gates, awaits the body, then re-checks only `busy`. Two concurrent `/complete` calls on a 0-byte file save it twice ("name (1)"); a cancel during the body read leaks a recreated part and session folder. Fix: run the session and file gates again after the body is read.
- **L3. Offer limits can be raced (Confirmed).** The one-session-per-sender and open-session checks ([receive_server.dart:765-777](../lib/core/server/receive_server.dart#L765-L777)) run before awaits, and the session is inserted only at :819. Parallel offers all pass. Fix: reserve the slot synchronously before the first await.
- **L4. Cancel during the peer check does nothing (Confirmed).** [send_controller.dart:418-422](../lib/features/send/send_controller.dart#L418-L422): while `peerCheckProvider` runs, `_prepare` and `_session` are null, so Cancel is a no-op and the send starts anyway.
- **L5. A new selection breaks a resumable send (Confirmed).** `_setPicked` ([send_controller.dart:159-168](../lib/features/send/send_controller.dart#L159-L168)) calls `_releaseLeftovers`, deleting the staging files of a send that failed with `canResume`, while its row stays `paused`. The next launch offers a Resume that can only fail with `source_unreadable`. Fix: mark that row failed when its files are released.
- **L6. Paused session keeps the server up with Receiving off (Confirmed).** `_stopIfIdle` ([receive_controller.dart:321-329](../lib/features/receive/receive_controller.dart#L321-L329)) treats `paused` as busy, unlike `_busy` (:334-344).
- **L7. Stale network binding flag (Plausible).** [network_binding.dart:29-46](../lib/app/network_binding.dart#L29-L46) runs `_apply` unawaited; an `onLost` during `bindToWifi(true)` lets the late result set `_bound = true` after Kotlin cleared the binding, so the next Wi-Fi without internet is never bound.
- **L8. Invisible Unicode in received names (Confirmed).** [file_name_sanitizer.dart:12](../lib/core/storage/file_name_sanitizer.dart#L12) does not strip bidi controls (U+202A to U+202E, U+2066 to U+2069) or zero-width characters, so `photo‮gpj.exe` is shown as `photoexe.jpg`. The saved collection uses the real extension, but the names in the UI and in Files are misleading.

## Speed for big files

Today the data path is serial on both phones:

- Sender ([upload_client.dart:440-466](../lib/core/client/upload_client.dart#L440-L466)): read 1 MB, `add`, `await flush()`, then read the next 1 MB. Disk reads and the network never overlap.
- Receiver ([receive_server.dart:1137-1176](../lib/core/server/receive_server.dart#L1137-L1176)): inside one `await for`, write 1 MB, hand it to the hasher, and every 4 MB `fsync` plus a database write. While any of these is awaited, the body stream is paused, the TCP window fills, and the sender stalls.

Suggested order, highest expected gain first:

1. **Measure first.** The Phase 7 benchmark has not been run. Add two bench-only toggles, "TLS off" (plain HTTP on the loopback or test network) and "hash off", plus the iperf3 baseline already described in BENCHMARKS.md, so each cost is known before changing code.
2. **Decouple network from disk on the receiver.** Keep reading the socket into a bounded queue (4 to 8 MB) and drain it from a separate writer loop that writes, hashes and checkpoints. The socket then keeps flowing while the disk is busy.
3. **Checkpoint less often.** `fsync` plus a SQLite write every 4 MB is costly on phone flash and through Android's FUSE layer. Checkpoint every 1 to 2 s or every 64 MB instead; after a crash this resends about 2 s of data, which is cheap. Update D-022.
4. **Read ahead on the sender.** Double-buffer: start reading chunk N+1 while chunk N is flushing. On Android every read is an `FdWorker` isolate round trip, so this hides that latency too.
5. **Fewer copies in `FdFile`.** [fd_file.dart:40-78](../lib/core/engine/fd_file.dart#L40-L78) zero-fills each buffer (`calloc`), then copies with `Uint8List.fromList`, then again with `TransferableTypedData`. Use `malloc`, or `pread` straight into a Dart `Uint8List` through a leaf FFI call (`isLeaf: true`, `.address`), and transfer without an extra copy. Same for `writeAt`.
6. **Native SHA-256.** `package:crypto` is pure Dart. Phone CPUs have SHA-256 instructions: CommonCrypto `CC_SHA256` on iOS, and a small C implementation with ARMv8 crypto extensions (or the platform's crypto) on Android, through FFI. On budget Android phones the receiver's hash may be the real ceiling, because the receive loop waits for it.
7. **Overlap files.** [send_session.dart:362-365](../lib/core/engine/send_session.dart#L362-L365) sends files strictly one after another: status, PUT, wait for the sender hash, then `/complete`, which on the receiver includes the final hash and the Photos or MediaStore publish. Start the PUT of file N+1 on a second connection while N completes, and start hashing the next file early. This matters most for batches of photos.
8. **Stream the iOS export.** D-038 exports each picked item fully to staging before the offer, so a 4 GB video is copied before any byte is sent. Offer once the size is known and upload while the export is still writing, or at least start sending file 1 while later items are prepared.
9. **Network choice.** Guide users to 5 GHz (iPhone Personal Hotspot with Maximize Compatibility off). Worth a test: an Android Wi-Fi Direct group with `WifiP2pConfig.Builder.setGroupOperatingBand(GROUP_OWNER_BAND_5GHZ)` (API 29+), which an iPhone joins as a normal Wi-Fi network, instead of LocalOnlyHotspot, which does not let the app choose the band.
10. **Parallel streams last.** As D-059 says, only if step 1 shows one stream well below the link while CPU is not the limit. It needs `pwrite` at arbitrary offsets on the receiver and a per-range (tree) hash instead of one running SHA-256.
